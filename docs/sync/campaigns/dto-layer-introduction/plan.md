
  Фаза 1: Розуміння поточного стану та створення DTO Snapshot

   1. Перегляд документації по синхронізації: Я вже прочитав docs/sync/SYNC_ARCHITECTURE_OVERVIEW.md. Я також перевірю наявність будь-якої іншої відповідної документації в папці docs/sync.
   2. Визначення всіх сутностей для синхронізації: Я проаналізую існуючий клас DatabaseContent та SyncLocalService, щоб отримати остаточний список усіх сутностей Room, які зараз є частиною процесу синхронізації/резервного копіювання. Це
      гарантує, що я створю снапшот для кожної необхідної сутності.
   3. Створення DTO Snapshot: Для кожної визначеної сутності я створю відповідний клас даних Snapshot. Я розміщу кожен клас снапшота у відповідному пакеті функції в data/snapshot відповідно до архітектурних правил.
       * Приклад: сутність Context -> features/contexts/data/snapshot/ContextSnapshot.kt.
       * Я використовуватиму наданий SnapshotBundle.kt як центральний агрегатор для всіх цих нових списків снапшотів.

  Фаза 2: Реалізація шару мапінгу

   1. Створення файлів мапінгу: Для кожної функції зі снапшотом DTO я створю файл snapshot/SnapshotMapping.kt.
   2. Реалізація розширення `toSnapshot()`: У кожному файлі мапінгу я створю функцію розширення toSnapshot(), яка перетворює сутність Room у відповідний DTO Snapshot. Я буду слідувати наданому прикладу Goal -> GoalSnapshot.
   3. Реалізація розширення `toEntity()`: Я також створю зворотну функцію мапінгу toEntity() у тому ж файлі.

  Фаза 3: Рефакторинг шару даних

   1. Оновлення `SyncLocalService`: Я проведу рефакторинг SyncLocalService (якщо він існує, або створю його на основі наданого вами шаблону).
       * Я зміню createFullSnapshotBundle для запиту необроблених даних з кожного DAO та використання маперів toSnapshot() для створення SnapshotBundle.
       * Метод applySnapshotBundle буде реалізований для прийняття SnapshotBundle, використання маперів toEntity() та вставки даних у базу даних за допомогою відповідних DAO.
   2. Заміна `DatabaseContent`: Я буду шукати використання старого класу DatabaseContent та замінювати його новим SnapshotBundle там, де це доречно (наприклад, у SyncFileService, MergeRepository тощо). Це критичний крок для переходу на
      нову архітектуру.

  Фаза 4: Оновлення логічного шару

   1. Оновлення `MergeRepository`: Я проведу рефакторинг MergeRepository, щоб він працював з DTO Snapshot (List<GoalSnapshot>) замість сутностей Room (List<Goal>). Основна логіка Last-Write-Wins (LWW) буде збережена, але адаптована для
      об'єктів снапшотів.

  Фаза 5: Зворотна сумісність та очищення

   1. Міграція застарілих версій: Мені потрібно буде дослідити, де найкраще розмістити LegacyMigrationMapper. Логічним місцем буде процес імпорту в SyncFileService. Коли JSON-файл буде прочитаний, я спочатку спробую розібрати його як
      SnapshotBundle. Якщо це не вдасться, я спробую розібрати його як старий DatabaseContent, а потім використаю LegacyMigrationMapper для перетворення DatabaseContent у SnapshotBundle. Це забезпечить зворотну сумісність.
   2. UI та дії: За вашим запитом, я прагнутиму додати нові дії в UI для імпорту/експорту на основі снапшотів, залишаючи старі на місці, щоб забезпечити безпечний перехід. Це означає, що я, ймовірно, буду додавати нові методи до
      SyncRepository і викликати їх з шару UI (ViewModel).
   3. Очищення: Я визначу та перелічу будь-які старі, тепер невикористовувані класи (наприклад, GoalDeserializer), які можна буде видалити після перевірки нової системи. Я не буду видаляти їх негайно, а запропоную їх видалення як
      останній крок.
