# Огляд архітектури та поточного стану синхронізації

Дата: 30 січня 2026

Цей документ описує архітектуру, поточний стан реалізації та відомі проблеми механізму синхронізації даних (кодова назва "Synapse") в додатку ForwardApp.

## 1. Високорівнева архітектура

Механізм спроєктований як модульна система, керована центральним фасадом.

- **`SyncRepository`**: Фасад і єдина точка входу для UI та інших частин програми. Він не містить власної логіки, а делегує завдання спеціалізованим компонентам.
- **`MergeRepository`**: Має відповідати за основну логіку злиття даних та вирішення конфліктів. На даний момент його реалізація не завершена.
- **`SyncFileService`**: Відповідає за функціонал імпорту/експорту даних у JSON-файли.
- **`WifiSyncService` / `WifiSyncServer`**: Реалізує peer-to-peer (P2P) синхронізацію між двома пристроями в одній Wi-Fi мережі.
- **`FullBackupLocalDataSource`**: Шар доступу до даних, що надає знімок бази даних для бекапу та виконує повне перезаписування БД при відновленні.

Стратегія вирішення конфліктів, закладена в дизайні — **Last-Write-Wins (LWW)**, де новіший запис (за полем `updatedAt`) перемагає.

---

## 2. Поточний стан реалізованих функцій

На практиці реалізовано та працює два незалежних механізми:

### 2.1. Імпорт/експорт повного бекапу в JSON

Це повністю реалізований, але ризикований функціонал.

**Як працює:**
- **Експорт**: `SyncFileService` збирає абсолютно всі дані з локальної бази даних та налаштунки, упаковує їх в один JSON-файл і зберігає в папку `Downloads/ForwardApp`.
- **Імпорт**: `SyncFileService` читає JSON-файл, **повністю стирає** всі поточні дані в додатку і записує на їхнє місце дані з файлу.

**Виявлені проблеми:**
1.  **Деструктивний імпорт**: Процес відновлення безповоротно знищує всі локальні дані, що були створені після моменту створення бекапу. **Це головний ризик для користувача.**
2.  **Відсутність перевірки версії схеми**: Система не перевіряє версію бекапу (`backupSchemaVersion`). Імпорт файлу з несумісної версії програми може призвести до збоїв або пошкодження даних.
3.  **Поверхнева обробка помилок**: Повідомлення про помилки неінформативні для користувача.

### 2.2. Peer-to-Peer синхронізація через Wi-Fi

Цей механізм дозволяє двом пристроям в одній локальній мережі синхронізувати дані напряму, без участі центрального сервера. Це може бути корисно для швидкого обміну даними між власними пристроями.

## 3. Застарілий код та рекомендації до рефакторингу

Під час аналізу було виявлено застарілий компонент:

- **`BackupRepository.kt`**: Цей клас є надлишковим. Він майже повністю дублює функціонал `SyncFileService` і не використовується основним фасадом `SyncRepository`.
  - **Рекомендація**: **Видалити `BackupRepository.kt`**. Єдиний унікальний метод `getLastSyncTime()` слід перенести в `MergeRepository`, оскільки він логічно належить до процесу злиття даних.

---

## 4. Загальний висновок та наступні кроки

Механізм синхронізації перебуває в стані активного рефакторингу. На даний момент **не існує повноцінної, безпечної хмарної синхронізації**.

**Поточний стан:**
- **Реалізовано**: Ручний імпорт/експорт через JSON та P2P-синхронізація через Wi-Fi.
- **В процесі**: Основна логіка злиття даних (`MergeRepository`) та інтеграція з центральним сервером.

**Ключові наступні кроки:**
1.  **Завершити `MergeRepository`**: Реалізувати надійний механізм злиття даних, можливо, розглянувши альтернативи простому LWW для уникнення втрати даних.
2.  **Покращити безпеку імпорту**: Додати в процес імпорту з файлу чіткі попередження для користувача та обов'язкову перевірку версії схеми бекапу.
3.  **Видалити застарілий код**: Прибрати `BackupRepository.kt`, щоб спростити кодову базу.
4.  **Реалізувати фонову синхронізацію**: Інтегрувати `WorkManager` для автоматичної синхронізації з сервером у фоновому режимі.
