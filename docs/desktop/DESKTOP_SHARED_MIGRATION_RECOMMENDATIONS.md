# Desktop Shared Functionality Migration Recommendations

Status: HISTORICAL

This document preserves an earlier Desktop/shared architecture direction from
the April 2026 migration work. It is not authoritative for the current Desktop
implementation or immediate project work.

Current Desktop implementation truth lives in the separate
`apps/day-goals-desktop/` repository. Parent-level cross-client architecture and
accepted decisions live in `docs/project/STATE.md` and
`docs/project/DECISIONS.md`.


## Огляд проекту та рекомендації щодо перенесення функціоналу в shared частину

На основі аналізу проекту ForwardApp, цей документ містить рекомендації щодо перенесення функціоналу з Android версії в shared модулі для підтримки десктопної версії.

### Поточний стан проекту

1. **Десктопний додаток вже початий**:
   - Має базову структуру з навігаційною панеллю
   - Вже реалізовано три екрани: Dashboard, Workbench, Settings
   - Використовується власна тема `ForwardDesktopTheme`
   - Є структура навігації з `DesktopDestination`

2. **Shared модулі вже існують**:
   - `shared-contracts` - для контрактів (DTO, enums, IDs)
   - `shared-domain` - для доменної логіки (use cases, parsers, mappers)
   - `shared-application` - для спільної логіки додатку

3. **Є чіткий план архітектури** в `DESKTOP_ARCHITECTURE_PLAN.md`

### Рекомендації щодо перенесення функціоналу

#### 1. Дотримуйтесь плану архітектури
Ваш план архітектури чіткий і правильний. Дотримуйтесь його послідовності:
1. Desktop shell and navigation (вже почато)
2. Desktop design system and layout primitives
3. Shared contracts module
4. Shared domain module
5. Read-only desktop context explorer
6. Desktop command palette
7. Editable backlog/inbox flows
8. Desktop persistence and sync

#### 2. Стратегія перенесення функціоналу

**Крок 1: Аналіз Android додатку**
Перш ніж переносити функціонал, потрібно зрозуміти, що саме є в Android додатку:
- Які сутності (entities) використовуються?
- Які use cases вже реалізовані?
- Які DTO, enums, IDs потрібні?

**Крок 2: Розширення shared-contracts**
Перенесіть у `shared-contracts`:
- Всі моделі даних (DTO)
- Enums та константи
- ID типи
- Інтерфейси репозиторіїв

**Крок 3: Розширення shared-domain**
Перенесіть у `shared-domain`:
- Use cases (випадки використання)
- Парсери та маппери
- Бізнес-правила
- Утиліти для роботи з текстом, markdown, пошуком

**Крок 4: Створення desktop-data адаптерів**
Для десктопу потрібні свої адаптери:
- Файлові сховища замість Room
- Локальні бази даних (SQLite через SQLDelight)
- Адаптери для синхронізації

**Крок 5: Поступове перенесення UI компонентів**
Переносіть UI компоненти поступово:
- Спочатку read-only компоненти (перегляд контекстів)
- Потім редагування (backlog, inbox)
- Нарешті, складні компоненти з синхронізацією

#### 3. Технічні рекомендації

**Для shared модулів**:
- Використовуйте чистий Kotlin (без Android залежностей)
- Використовуйте Kotlin Multiplatform, якщо потрібна підтримка iOS у майбутньому
- Створюйте чіткі інтерфейси для репозиторіїв
- Використовуйте dependency injection через інтерфейси

**Для десктопу**:
- Використовуйте Compose Desktop для UI
- Для локального зберігання використовуйте SQLDelight або файлові сховища
- Для конфігурації використовуйте файли (JSON, YAML)
- Реалізуйте нативні шорткати та меню

**Для синхронізації**:
- Створіть спільний модуль для логіки синхронізації
- Використовуйте різні адаптери для Android та десктопу
- Реалізуйте офлайн-роботу з конфлікт-резолюцією
- Використовуйте спільні формати даних для експорту/імпорту

#### 4. Конкретні наступні кроки

1. **Завершіть базову структуру десктопу**:
   - Додайте повноцінну навігацію між екранами
   - Розробіть дизайн-систему з компонентами
   - Створіть базові UI компоненти (кнопки, поля вводу, списки)

2. **Проаналізуйте Android додаток**:
   - Вивчіть структуру пакетів у `app/src/main/java/com/romankozak/`
   - Визначте ключові сутності та use cases
   - Створіть список функціоналу для перенесення з пріоритетами

3. **Розпочніть перенесення контрактів**:
   - Перенесіть основні моделі даних (Note, Context, Task тощо)
   - Створіть інтерфейси репозиторіїв для цих сутностей
   - Визначте спільні enums (Status, Priority, Type тощо)

4. **Створіть перший вертикальний зріз**:
   - Виберіть простий функціонал (наприклад, перегляд нотаток)
   - Перенесіть його повністю (контракти + домен + UI)
   - Переконайтеся, що працює на обох платформах
   - Протестуйте на Android та десктопі

### Принципи успішного перенесення

1. **Поступовість**: Не намагайтеся перенести все одразу. Почніть з простого.
2. **Тестування**: Кожен перенесений компонент має працювати на обох платформах.
3. **Ізоляція**: Shared код не повинен залежати від платформних API.
4. **Гнучкість**: Архітектура має дозволяти легко додавати нові платформи.
5. **Документація**: Документуйте процес перенесення та архітектурні рішення.

### Перевірка прогресу

Регулярно перевіряйте:
- [ ] Чи збирається десктопний додаток
- [ ] Чи збирається Android додаток після змін
- [ ] Чи працюють тести в shared модулях
- [ ] Чи відсутні залежності на Android API в shared коді
- [ ] Чи можна використовувати shared код на обох платформах
