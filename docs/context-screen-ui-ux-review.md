# Огляд Екрану Контексту: UI/UX Рекомендації

Цей документ фіксує основні UX/UI проблеми поточного екрана контексту та пріоритетні покращення, які можуть вивести його на рівень справді сильного продуктового досвіду.

## Головні проблеми

1. Екран перевантажений рівнями навігації й керування.

- Одночасно присутні top bar, view mode switch, navigation bar, input panel, контентні меню, selection bars і bottom sheet-и.
- Користувач постійно перемикає увагу між "де я?" і "що тут натиснути?".

2. Архітектура дій прив’язана до типу view, а не до наміру користувача.

- Дії розкидані між backlog item menu, top bar, input panel, capability action sheets.
- Для сильного UX потрібен intent-first підхід: `захопити`, `уточнити`, `перемістити`, `спланувати`, `пов’язати`.

3. Контекст як сутність ще недостатньо "живий".

- Немає сильного summary state у верхній частині екрана.
- Бракує відповіді на питання:
  - що це за контекст
  - що тут головне зараз
  - що потребує уваги
  - що прострочено
  - який наступний найкращий крок

4. Dashboard/View mode модель сильна для power-user, але дорога по когнітивному навантаженню.

- Користувач фактично стрибає між окремими мікроекранами, а не працює в одному цілісному просторі.

5. Capture flow недостатньо оптимізований під швидкість.

- Додавання в inbox/backlog/план має займати мінімум дій.
- Система повинна агресивніше допомагати, а не змушувати обирати режим вручну.

6. Слабке відчуття прогресу і payoff.

- Є багато функцій, але мало моментів, де екран показує:
  - що саме зрушилось
  - що було очищено
  - що стало наступним пріоритетом

## Базовий UX-принцип

Для цього екрана варто зберігати `payload-first` підхід.

Сила поточної моделі в тому, що користувач бачить один конкретний вид даних і може одразу працювати з ним. На малому екрані це критично важливо. Будь-який великий header, summary block або "hero section" ризикує з'їсти робочу площу й зробити екран менш продуктивним.

Тому головний напрямок покращення:

- не збільшувати верхню частину екрана
- не додавати важкі summary-блоки над контентом
- зберігати максимум площі під payload
- зменшувати chrome навколо основного вмісту

## Що дасть найбільший приріст

### 1. Компактний context status strip замість hero block

Замість великого верхнього блоку краще мати дуже компактний status strip:

- назва контексту
- короткий статус
- 1-2 мікроіндикатори
- опційно один критичний CTA

Все інше має або розкриватися за запитом, або жити в окремому review-режимі.

### 2. Спрощення сценаріїв

Замість великої кількості view modes варто мислити через 3 основні сценарії:

- `Capture`
- `Work`
- `Review`

Більшість поточних capability views можна сховати всередині цих сценаріїв.

### 3. Один smart input як головний двигун екрана

Нижня панель вводу має стати основним центром дії:

- один розумний input
- quick chips:
  - `В inbox`
  - `В backlog`
  - `У план`
  - `Нагадування`
  - `Пов’язати`

Система має пропонувати дефолтний маршрут введеного тексту.

### 4. Next Best Action

Для кожного контексту можна показувати одну найкращу рекомендовану дію, але без роздування верхньої частини екрана:

- `Очистити inbox (4)`
- `Є 2 прострочені нагадування`
- `Немає жодної активної цілі`
- `Перенести 3 ідеї в план`

Це підсилює відчуття "розумного" продукту, якщо реалізовано компактно.

### 5. Об’єднаний робочий режим

Замість постійних переходів між inbox і backlog варто дати composite flow:

- зверху inbox triage
- нижче active backlog
- нижче completed або cold items

Це природніше для щоденної роботи.

### 6. Clipboard як signature behavior

У застосунку вже є сильна модель copy/cut/paste між сутностями. Це можна зробити ключовою продуктовою фічею.

Потрібно:

- глобально показувати стан clipboard
- чітко показувати, що зараз вирізано/скопійовано
- дозволяти швидке вставлення в інший контекст

## Конкретні UX покращення

### Глобальний clipboard/status chip

Якщо щось скопійовано або вирізано, користувач має бачити це без відкриття меню.

### Сильніша візуальна ієрархія backlog items

Елементи мають швидко скануватись по стану:

- активне
- заплановане
- заблоковане
- прострочене
- завершене

### Thumb-first mobile use

Менше дрібних іконок у верхній частині екрана і менше постійного chrome.

Більше головних дій:

- у нижній зоні
- у sticky action strip
- у компактних grouped sheets

### Focus context session

Потрібен спрощений режим для роботи всередині одного контексту:

- головна ціль
- наступні кроки
- таймер або трекінг
- мінімум шуму

### Review layer

Окремий шар для регулярного перегляду:

- `Нове`
- `Потребує рішення`
- `Заплановано`
- `Чекає`
- `Завершено`

Це краще, ніж просто показувати сутності як список.

### Rich empty states

Порожній екран має не просто повідомляти про порожнечу, а пропонувати наступну дію.

## Що робити першим

1. Зберегти payload-first модель і зменшувати все, що відволікає від основного вмісту.
2. Перетворити верхню частину на компактний status strip замість великого summary-блоку.
3. Уніфікувати capture flow через один smart input.
4. Винести clipboard/status у глобально видимий, але компактний елемент.
5. Додати unified work mode: inbox triage + active backlog на одному полотні.
6. Перепакувати view modes у більш людські сценарії: `Capture / Work / Review`.

## Очікуваний результат

Якщо впровадити ці зміни, екран контексту стане:

- швидшим у щоденному використанні
- зрозумілішим на малих екранах
- щільнішим по корисному payload
- сильнішим по відчуттю фокусу
- більш "живим" у плані стану і рекомендацій
- ближчим до рівня killer app, а не просто функціонального комбайна
