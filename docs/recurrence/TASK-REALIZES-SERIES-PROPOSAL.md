# Recurring task Realizes defaults

Status **PROPOSED**. The current [Day Task Realizes contract](../architecture/CANONICAL-PLANNING-CONTRACT-V3.md#current-day-task-notes-and-realizes-2026-10-20) and [recurrence-v2 contract](RECURRENCE_V2_ANDROID_CANONICALIZATION_DEBT.md) remain authoritative until this proposal is accepted and implemented.

## Current authoring paths

| Path | Current behavior |
| --- | --- |
| Task Properties → Realizes | `TaskRealizesViewModel` immediately writes the task's concrete `realizedDayFocusItemIds` through `DayTaskRealizationRepository.toggle`, or updates the day's task-keyed theme assignment through `DayThemeRepository.update`. Selected priorities can suggest themes, which require explicit acceptance. Other references use their existing PlanningReference path. |
| New task / enable Repeat | `DayPlanViewModel` calls `CanonicalTaskRecurrenceAuthoringAdapter.createSeriesForPlan`. `EditTaskViewModel.saveRecurringTask` calls `convertOneOffToSeries` for a one-off, rereading the current task after immediate Realizes writes. Conversion replaces the task ID with the deterministic series/day occurrence ID. The adapter copies concrete priority links and rebinds Planning references, but it does not rekey Day Theme assignments. Split and detach also replace task IDs without rekeying those assignments. |
| Existing series edits | `EditTaskViewModel.saveRecurringTask` uses `updateSeriesTemplate` for an unchanged rule. That method updates the selected row and qualifying template-matching rows, including earlier days. A changed rule uses `splitSeriesFromOccurrence`. `DayPlanViewModel.updateTask` has a separate branch between `updateCurrentOccurrence` and a split even when the rule is unchanged. Neither branch currently edits Realizes defaults. |
| Open day / materialize | `DayPlanViewModel` calls `DayManagementRepository.materializeCanonicalRecurrenceForDate`. `CanonicalRecurrenceMaterializationAdapter` applies the shared materializer in a Room transaction and writes tasks before priorities. It attaches or repairs Planning SOURCE metadata, with no equivalent for inherited Realizes links. |

A Day Theme assignment can become stranded when a task acquires a replacement ID. Repairing that ownership during same-day replacement is part of this proposal. An independent template edit can currently change content on earlier materialized days. Aligning general Properties edits with date-scoped intent is a separate product decision. A focused edit-scope correction and regression coverage would be small to medium, depending on the chosen behavior. It need not block a Realizes-specific command.

## Proposed ownership and edit behavior

- Add typed defaults to the shared TASK series template. A theme default names the stable `ThemeDefinition.id`. A priority default names a canonical FOCUS or RESPONSIBILITY series ID. A day's theme occurrence ID, concrete priority item ID and display title are inputs for resolving current selections. They have no template authority. Reject TASK series as priority targets. Keep explicit one-off priorities as same-day concrete links.
- Give each recurring task occurrence a durable Realizes override keyed by stable target identity. The recommended shape supports adding a target for that occurrence, excluding a default for that occurrence and returning either state to inheritance. An exclusion must survive even when the target has yet to materialize. Preserve occurrence-local concrete selections independently and retain enough provenance to remove an inherited link without deleting an explicit selection of the same endpoint.
- Keep the published same-day links in their current owners. Day Theme assignment documents own concrete task-to-DayTheme membership and `DayTask.realizedDayFocusItemIds` owns concrete same-day priority links. The template and occurrence override govern which links reconciliation may write. These records are `SEMANTIC_NOT_HIERARCHY`. SOURCE, RELATED, scheduling, completion and general hierarchy keep their existing authorities.
- Conversion reads the live task and its Day Theme assignment within the recurrence transaction. Preserve the exact same-day concrete selections and rekey task-owned assignments to the new task. Treat enabling Repeat as the series intent: initialize the new template from the selected definitions and recurring priorities. A one-off priority remains on the converted day's task. Apply the same rekey rules to replacements during split/detach, carrying overrides for same-day replacements that remain in a series. For a detached task, retain concrete same-day links and stop future inheritance.
- **This occurrence** writes only its override or concrete link and reconciles that task. **This and future** changes defaults effective on the selected recurrence day key, including the selected day. Use a date-scoped series operation even if the rule is unchanged. Reconcile existing live occurrences on or after the boundary as well as later generations. Use the date guard independently of whether title or other content still matches the template. Preserve explicit overrides and removals, prior dates and deleted occurrences. A Realizes-only edit should leave task content and scheduling alone.

## Resolution, retries and transport

Resolve each effective default against the task's exact live DayPlan. Look up the active DayTheme for the definition and the live priority occurrence for the target series on that day. Treat absent, inactive, deleted and wrong-day endpoints as unavailable. The proposed behavior leaves the intent pending when a matching target simply arrives late and does not create a theme or priority or move it to another day. A priority whose schedule does not match contributes no link for that day. Exact IDs control resolution.

Reconcile after task and priority insertion and whenever Day Theme preparation or accepted sync makes an exact endpoint available. Reuse that reconciliation for existing eligible occurrences and apply each change transactionally with its affected rows. Retry reads the winning series revision and live task, override and endpoint state. Missing-target repair must respect explicit exclusions, current default removal, and task/endpoint tombstones. Derive only a set difference with known inherited provenance. A replay with no effective change writes no extra version or link. This work depends on the persisted DayPlan identity used by both endpoints and cannot substitute for the [same-day planning merge work](../sync/architecture/ANDROID-SAME-DAY-PLANNING-MERGE.md).

Extend the shared recurrence model and Android's explicit stable-key `TaskRecurrenceSourceMapping` codec. Carry defaults through the existing `CanonicalRecurringSeriesSnapshot.template` object and assign occurrence intent/provenance an explicit versioned wire shape. Verify full backup, exact Restore, delta and changed-since, selective import closure and exact-version ACK for any affected record. An old template or occurrence with absent fields supplies no new intent. Absence in a legacy merge preserves newer local intent. Explicit empty/default removal and override reset need a distinct representation and freshness check. Validate typed targets, preserve pending IDs and reject malformed fields. Preserve stale-replay protection for removals and detect incompatible concurrent intent rather than using derived links to decide the winner. Keep the current incoming concrete-link semantics for pre-feature payloads.

The numeric bundle version alone does not prove compatibility. Android's older task-series writer rebuilds the known JSON keys, so an unknown field can survive transport yet disappear on series edit. Check old Android and Desktop read, re-export and write paths, including the shared JS facade. Allow legacy writes affecting protected state only after proving lossless preservation or gating those writes by peer capability. Review exact Restore separately from Merge. Older backups should restore their supplied concrete links with no inferred inheritance.

## Decisions needed before implementation

- Approve whether a template selection should follow a target priority after its series splits. A split allocates a new series ID. Exact-ID resolution follows only the chosen segment unless an explicit, versioned successor mapping or retarget command is adopted. Exclude title or source-Orientation matching.
- Use the existing occurrence/forward scope choice for Realizes edits. Confirm whether series selectors may choose a ThemeDefinition that is unavailable on the selected day. This proposal leaves that default dormant until ordinary day preparation creates the eligible DayTheme.
- Choose the occurrence override and provenance persistence shape, the forward-only series representation for unchanged rules, the rule for completed future occurrences, and freshness handling for concurrent series/override edits. Approve the mixed-version peer capability strategy and whether rollout requires Desktop writes in the first slice.

## Acceptance

Use two supported Android devices with the same planning calendar. Create a one-off task with a theme, a recurring priority and a one-off priority. Convert it and verify all same-day selections follow the task's replacement ID. Verify the template was initialized from eligible selections and a later matching occurrence receives its own DayTheme and priority IDs. Verify previous dates and explicit one-off links stay day-local. Repeat the checks for task split and detach.

On the second device independently materialize a future occurrence before a **this and future** edit. Apply that edit, sync in both directions and check already-generated and newly-generated occurrences. On one device exclude a default for one task occurrence, then sync the target later and replay an older payload. Verify the exclusion survives while unaffected occurrences inherit. Repeat for removal of a series default, target deletion and an already-deleted task. Check duplicates, convergence of logical links, and no-op replay, then restart both apps and verify Realizes and task cards. Exercise full Restore, delta/selective exchange and an older peer's protection path with representative fixtures. Record physical results separately from host tests.
